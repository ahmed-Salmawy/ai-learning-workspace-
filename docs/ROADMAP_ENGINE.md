# Roadmap Engine — Roadmint Analysis & Integration Verdict

Last Verified: 8319ed1 (2026-09-11)

Source inspected: https://github.com/Shresht-Ahuja/Roadmint (clone of HEAD `e03afce`, 2026-09-11).

This document answers README §62 Step 2: what is Roadmint, what is reusable, and what must stay behind the `RoadmapEngine` abstraction.

## 1. What Roadmint Actually Is

A ~3,700-LOC Streamlit demo app, not a library. No package structure, no `pyproject.toml`, no tests, no DB, no persistence. Key components:

| File | Role |
|---|---|
| `train.py` | LoRA fine-tune of `google/gemma-2b` (r=16, q_proj/v_proj) on a synthetic 1,000-sample JSONL |
| `roadmap_dataset_large.jsonl` | Synthetic prompt/completion pairs ("I want to learn X" → "Step 1: ...\nTime: 2 days") generated by `scrape3.py` |
| `loading_my_model.py` (909 LOC) | Model loading, roadmap generation w/ retry+validation, link enhancement, `RoadmapEvaluator` |
| `pdf_mode.py` | "Topic extraction" from PDFs |
| `web_crawling.py` | `LinkFinder` — W3Schools/GfG URL construction + HEAD probing, curated YouTube dict, `youtubesearchpython` fallback |
| `roadmap_evaluator.py`, `reference.py` | Training-era evaluation tooling (structure score, MiniLM semantic similarity vs a curated `reference.txt`) |
| `streamlit_app.py` | Demo UI, model comparison tabs |
| `gemma-roadmap-lora-final/` | Committed LoRA adapter weights (~7 MB) + tokenizer |

## 2. Hard Technical Findings (verified from code)

1. **Output is unstructured prose.** Roadmaps are plain-text blocks (`title\ndescription\nTime: ...\nLink: ...\nYouTube: ...`) parsed back with regex (`extract_roadmap_steps`). Directly conflicts with our invariant: persisted AI outputs must use validated structured schemas (README §33).
2. **PDF "extraction" is `lines[1]` per page.** `pdf_mode.py:15` takes the *second line of every page* as a subtopic. Works only for slide decks. No TOC detection, no chapters, no semantic chunking, no provenance, no page-range tracking. Unusable for real books.
3. **No dependency awareness.** The roadmap is a flat ordered list. No prerequisites, no DAG, no `PREREQUISITE_OF`, no roadmap versioning — all core requirements of README §10.
4. **GPU-bound runtime.** Gemma-2B with `bitsandbytes` 4-bit quantization and CUDA device maps (`gemma_loader.py`). Not deployable in our planned FastAPI/Postgres stack without GPU infrastructure.
5. **Model quality ceiling.** Fine-tuned on 1,000 synthetic samples for generic web-dev skills. Hardcoded description/time-estimate dictionaries (`pdf_mode.py:105-173`) — lookups, not intelligence.
6. **Scraper fragility.** Link discovery is URL-pattern guessing + HTTP HEAD probing against W3Schools/GfG, with hardcoded topic dicts. Brittle, rate-limited, and web-dev-biased; irrelevant to book-grounded learning.
7. **Concept extraction: absent.** Roadmint extracts no concepts and builds no knowledge graph. "Topics" are page-2nd-lines.

## 3. Verdict: Reusable vs Abstraction Boundary

### Reuse as code/model: NONE

- Do not vendor Roadmint code.
- Do not ship the fine-tuned Gemma adapter as our generation engine.
- Do not adopt the regex-parsed plain-text roadmap format.

### Reuse as ideas: LIMITED, deliberate

| Idea from Roadmint | Disposition |
|---|---|
| Engine interface shape (generate / extract topics / attach resources) | Reflected in our `RoadmapEngine` protocol (below), extended with `buildDependencies` + versioning |
| Structure scoring of generated roadmaps (steps have title/desc/time/link) | Candidate for a post-generation *validator* in `LLMRoadmapEngine` (schema check + completeness ratio), not a training evaluator |
| Semantic similarity (MiniLM) for roadmap-vs-source coverage | Possible future quality metric comparing roadmap concepts vs extracted concepts; not Phase 1/2 |
| PDF heuristic (`lines[1]`) | Negative reference — cited as the cautionary tale justifying real TOC detection + semantic chunking (§7 of README spec) |
| Resource discovery (external links) | Out of scope for Phase 1/2; if ever needed, it is a separate `ResourceDiscovery` concern, never inside `RoadmapEngine` |

### What stays behind `RoadmapEngine`

Everything generation-related. The application owns learning state; the engine is stateless-with-respect-to-us and swappable:

```text
RoadmapEngine (protocol)
├── generateRoadmap(bookContext) -> RoadmapDraft
├── regenerateRoadmap(bookContext, priorRoadmap, learnerState) -> RoadmapDraft   # idempotent, preserves history
├── extractConcepts(chunks) -> list[ConceptDraft]
└── buildDependencies(concepts) -> list[ConceptEdge]

Implementations (planned):
├── LLMRoadmapEngine        # initial: LLMProvider + schema-validated JSON output (ADR-001)
├── RoadmintRoadmapEngine   # only if a GPU runtime + structured-output wrapper is ever justified
├── GraphRoadmapEngine, ManualRoadmapEngine   # future
```

`RoadmapDraft` is a validated Pydantic model (nodes, edges, priorities, difficulty, estimates, sourceSections) — never raw prose. The engine never writes to the DB; a deterministic orchestrator versions and persists.

## 4. Consequence for Sequencing

README §3 named `RoadmintRoadmapEngine` the *initial* implementation. The code inspection shows that adapter would require GPU infra and a prose-parsing shim that violates README §33. Decision (ADR-001): implement the `RoadmapEngine` interface + `LLMRoadmapEngine` (structured output) first; keep `RoadmintRoadmapEngine` as a possible future adapter. This preserves the README's hard requirement (no tight coupling) and its "possible future implementations: LLMRoadmapEngine" path; it changes only which adapter ships first. Flagged to the product owner in `SESSION_HANDOFF.md`.
